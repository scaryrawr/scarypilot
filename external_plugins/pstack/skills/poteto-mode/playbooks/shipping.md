### Shipping

**You own what lands. Verify each PR independently and merge or enqueue only the approved verified prefix through an explicit ceiling.**

This is the half after `playbooks/babysit.md`. Babysit makes a stack mergeable. Shipping decides what is safe to merge. `github/gh-stack` merges the selected lower prefix directly or submits it to the repository's merge queue. This is an explicit merge operation, not merge-when-ready. Green is not safe, and the gap between those two words is where this playbook lives.

1. **Verify every PR independently before merging or enqueueing anything.** One subagent per PR, not batched, each a background Copilot agent, each exercising the real surface (the project verification skill or available UI/CLI tools) against parent versus head. Each returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR so the record outlives the chat. Append `- Generated with AI 🤖` once to each agent-authored published verdict. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable, because merging it would pull the gap in underneath it. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that the verdicts still describe the code.** A restack rewrites every SHA above it and silently invalidates every verdict without touching a single check. Record the verdict head SHA, the verdict base SHA, and the stable `git patch-id` for that PR's base-to-head diff. Compare that patch-id against the current head before trusting an older verdict. When the two patches differ only in tests, docs, or lint config, rebuild what each lane ran: twice at the verdict SHA and once at the current head. A difference is noise if the same difference already shows up between two builds at the verdict SHA, or if it is only an embedded commit SHA. Judge each difference on its own, not by file, and report each kind of noise with the files it covers. If only noise differs, the lane's result stays valid and only checks and a fresh review of the change run again. When the patch-id is unchanged, re-run mergeability and CI at the current head before trusting the verdict. Never reuse a lane result that came from a dev server or anything else with no build output; rerun that lane. Re-verify anything else that actually drifted. Twenty-one verdicts went stale this way in one run with no signal at all.

   **Base freshness takes precedence over patch-id or build-noise reuse.** If trunk or the intended parent/base changes, rerun CI and required live/perf lanes against the combined current base and PR head, and refresh the exact base/head receipts. A clean merge and non-overlapping paths do not establish integration safety. A forge's green merge-queue or latest-merge result is equivalent only when it identifies that exact combined tree and includes the required live/perf evidence; green checks on a stale head are not equivalent. Until this proof exists, do not reuse old integration results or authorize landing.
4. **Obtain approval for the exact prefix and resolve the ceiling before merging.** Confirm `ghStack` capability and the complete bottom-to-top PR list. Report the intended repository, root, ceiling PR, included PRs, current head/base receipts, and merge method to the user. Approval to build, adopt, submit, or reach merge-ready does not authorize merging. Require approval that covers this exact prefix. Do not install or adopt a stack as a fallback.

   `gh stack merge <verified-ceiling-pr>` merges or enqueues everything below that PR, including the PR itself. Released v0.2.1 resolves a bare number as a **stack number first**, then as a PR number. Prove that the numeric target resolves to the intended stack and exact approved prefix before execution. If that cannot be established, stop for the operator to inspect and confirm the actual selection. An interactive picker does not grant broader scope. In a noninteractive host the command proceeds without a prompt, so never use the command itself as a discovery probe. Do not run a bare whole-stack merge or add `--yes` to bypass unresolved scope.
5. **Keep readiness gates outside the merge command.** gh-stack checks basic PR state, while GitHub evaluates repository rules. Neither substitutes for steps 1–3. Reacquire live head/base identities, CI, reviews, draft state, and mergeability for every included PR immediately before the approved operation. Any drift invalidates the approval's evidence and returns to verification. Never enable child-PR GitHub auto-merge to emulate stack merging. If unexpected auto-merge is already armed, stop and obtain scope to correct it rather than silently mutating the stack.
6. **Confirm the actual outcome, not an armed-state fiction.** Record which approved PRs merged or which exact prefix entered the native queue. Check live GitHub state and the operation's result; `autoMergeRequest` alone proves neither selected scope nor queue admission. A queue can process groups separately. Do not promise a sequential drain or extend the ceiling because other PRs are green.
7. **Once submitted to the queue, stop touching the stack.** No `gh stack sync`, rebase, push, link, add, or submit while an approved prefix is in flight. These are topology or publication mutations, not status probes. Independent work stays outside the submitted prefix. A failed or uncertain merge command does not authorize a blind retry; reacquire the complete stack and live lifecycle, report what actually happened, and obtain any renewed scope before another mutation.
8. **Watch outcomes, do not drive the queue.** Run the Bun watcher in queued mode over the frozen approved PR list as a background command until COMPLETE at the ceiling. It observes GitHub only and never merges or enqueues. ADVANCE reports observed progress, not permission for another merge. Re-arm after a verdict you act on without rediscovering a shorter list that loses retargeted descendants. If the queue stalls or errors, report the blocker and stop before further mutations. Direct merges can complete without a queue; confirm every included PR is actually merged.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1, not a judgment call you make at 3am.

**Reply:** the approved prefix and ceiling, each PR's verdict and verifier, the exact target resolution and operation, what merged or entered the queue and how you confirmed it, and what the next gap needs.
