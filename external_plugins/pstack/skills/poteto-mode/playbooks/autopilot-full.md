### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program with the same one-owner-per-PR rule. Here the queue is independent, each owner carries the whole lifecycle, and the root keeps verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go. On that go, persist the full program objective in the decision trail. Re-read it at every audit until the queue is done.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** One background Copilot agent in an isolated worktree or project session per PR owns build, first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip through `/deslop` and `/unslop`, `/no-comments`, a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Use **Opening a PR** for host tools and forge operations; independent PRs do not require gh-stack or stack adoption. Within about 15 minutes, every owner starts a `decisions.tsv` trail, pushes a first branch snapshot, and opens its PR before self-proof. After that, push after every verifiable unit with hooks on. Keep the trail uncommitted and return it with reports. Track child agent IDs, expected runtimes, and states in a separate `children.tsv`. The owner rebases before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, keep that merge base. Rebase again only at merge prep, on a conflict with trunk, or on a CI failure caused by trunk. After the slop-strip and `/no-comments`, report the code-ready head SHA and each later push that changes the patch. Self-proof, CI, and babysit run in parallel with the swarm. Report merge-ready with the head SHA when they finish. Before a PR-facing push, run the repository's pre-review checks on the committed head. A hook pass is not self-proof. Publish a rebase only to the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The merge is the one step an owner may not take alone; step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify the finished code once.** At the owner's code-ready head, fan out independent verifiers per the **swarm** skill. Run another full swarm for new behavior, a redesign, or a large new diff. A rebase, conflict resolution, or minor fix gets a single verifier at the new head. A wording-only edit that changes no behavior or executable guidance needs no extra verifier, but still needs a current-head receipt audit and accurate shipped docs. Required gates and integration evidence are never waived by that exception.

   Re-run gates, prove load-bearing behavior through the project verifier or available UI/CLI tools, and audit the diff without trusting the PR body. Results remain provisional until the owner reports merge-ready. Then audit the final self-proof, CI, and babysit receipts against the exact head and required pass predicates. Missing, stale, or failed evidence blocks acceptance. The live lane remains mandatory for behavioral changes. Apply `playbooks/shipping.md` to any lane reuse and base movement.

   Block only for a problem demonstrated by a failing run at the head or a shipped doc line the PR made wrong. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks; park other findings as follow-ups. A problem already present on the base does not block unless the PR copies it or newly reaches it. Send blocking findings to the owner in one fix-forward with repro evidence, never write their branch yourself. Every updated ready report needs a fresh receipt audit.
5. **On a clean verdict the owner merges, and a fresh owner takes the next item.** Merge prep follows the round's lanes and rebases onto current trunk. Record the tested trunk/base SHA and resulting head SHA. CI and required live/perf lanes must pass on that combined tree, and the root repeats the receipt audit from step 4. Immediately before merge, fetch trunk and compare its SHA with the tested base. Any base movement invalidates those integration receipts even when paths do not overlap, `git merge-tree` is clean, or the PR's patch-id is unchanged. Rebase onto the new trunk, rerun CI and required live/perf lanes, refresh the exact base/head receipts and root verdict, and repeat the check. The alternative to another rebase is a forge merge-queue or latest-merge result for the exact current base and PR head, with green CI and the required live/perf evidence on that combined tree. A green head check alone is not equivalent. Use `playbooks/shipping.md` only for lane reuse that its base-freshness rule permits. The owner squash-merges its own PR and returns. A fresh owner takes the next independent item with a complete brief. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer on an hourly audit tick.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. A disabled or soft-failed check does not guard its cases and is not a passing gate. Never bypass forge-enforced approvals. Absorbing values that already landed on main is drift, not a raise. On the operator's go, schedule the hourly audit with the host's session automation when available and approved. Otherwise use one bounded timer while the session remains active and state that it cannot wake a closed session. Process completion notifications as queue events; do not poll or rely on memory for the cadence. At each audit, re-read this playbook and the persisted objective. Probe known running owners with `read_agent` or the host's session status tool and collect their decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Check the pushed branches and `children.tsv` too. Treat errors, inability to start a turn, or exceeding the expected runtime without a side effect as stuck. Record the gap and use available stop or hold controls before dispatching a replacement; do not allow two writers on the same branch. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. Catch the operator up through the **ketchup** skill when the tick changes something for them; unchanged ticks stay quiet. Stop the audit schedule when no delegated work remains, including after the last merge.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

In step 2's fix rounds, a known concurrent change landing in the same files also requires rebasing. Push each finished, verified unit before starting the next. Neither this cadence nor a clean verdict overrides the operator's gates or grants missing external-write or merge authority.

**Reply:** catch the operator up through the **ketchup** skill. Cover each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups. Link to each PR and the collected trails for owner, head, and verification details rather than copying the ledger into chat.
